# dsh-deputy 设计思路

## 0. 一句话

> 把「桌面」当成一个**变化稀疏**的信号源，而不是一叠待截图的画面：
> 本地持续打分，只在跨档时把帧压进一张 4×4 联系表送进会话；动作优先走 UIA 语义，
> 每一步只校验它本该影响的那块区域。

---

## 1. 要解决的真问题

参考 `dsh-computer-use-win`（MCP + PowerShell UIA 后端）和 `dsh-see-now`（变化打分 + 4×4 拼图）
之后，桌面代理卡住的不是"能不能点到"，而是三件事：

| 瓶颈 | 现象 | 代价 |
|---|---|---|
| **感知通胀** | 每一步都截一张全屏图丢给模型 | 10 步任务 ≈ 10 张图 token；长任务直接吃光上下文 |
| **定位脓性** | 纯坐标点击，UI 一挪位就点空，点空还看不出来 | 静默失败 → 越点越偏 → 死循环重试 |
| **焦点争夺** | 自动化进程和用户抢同一块桌面 | 用户一动鼠标，任务就断 |

deputy 的三条主线就是对着这三条来的：

1. **变化即证据**：帧的价值 = 它相对上一帧"变了多少"，不是"它有多清楚"。
2. **语义优先**：能用 UIA pattern 就别发键鼠；键鼠是兜底，不是首选。
3. **ROI 校验**：动作是否生效，看它该改的地方改没改，外加"别处有没有被带脏"。

## 2. 整体架构

```
                    ┌─────────────── ISOLATE 层 ───────────────┐
                    │ 独立 Window Station/Desktop + 受限令牌    │
                    │  + Job Object 限资源，不抢主桌面焦点       │
                    └──────────────────┬───────────────────────┘
                                       │ 桌面内采帧
   ┌──────────┐   灰度帧   ┌───────────▼──────────┐   跨档帧   ┌──────────────┐
   │ SENSOR   ├───────────►│ SENSE  diff/sheet    ├───────────►│  SESSION     │
   │ capture  │            │  dHash + 网格变化     │  4×4 PNG  │ attachments  │
   └──────────┘            └───────────┬──────────┘            └──────────────┘
                                       │ 变化包围盒 box
                                       ▼
   ┌──────────┐  ref   ┌────────────┐  action  ┌────────────┐  ROI  ┌──────────┐
   │ UIA tree ├───────►│  DECIDE    ├─────────►│  ACT       ├──────►│ VERIFY   │
   │ (PS 后端)│        │ (宿主模型)  │          │ UIA→input  │       │ roi.mjs  │
   └──────────┘        └────────────┘          └────────────┘       └────┬─────┘
                                            verdict: ok / no-effect / side-effect
                                                                        │
                                            ┌───────────────────────────┘
                                            ▼
                                   BUDGET：超预算则降级或收手
```

六层各管一件事，层与层之间只传结构化数据（帧 / 分数 / ref / action / verdict），
不传"自然语言理解结果"，所以每一层都能单独测（见 `test/run-tests.mjs`）。

## 3. 六个关键决策

### 决策 1：感知分档，不是"要么看要么不看"

`scoreFrame` 输出 0..1 的分数并映射四档：

| 档位 | 含义 | 典型场景 | 是否进会话 |
|---|---|---|---|
| `still` | 没动 | 空闲、等加载 | 否 |
| `minor` | 小动静 | 光标闪烁、秒针、加载动画 | 否 |
| `meaningful` | 有意义的界面变化 | 菜单展开、页面跳转 | 是（默认阈值） |
| `major` | 大改 | 新窗口、弹窗、整个视图切换 | 是，且优先占位 |

分数由两个信号加权：`0.4 × dHash 距离` + `0.6 × (网格变化占比 + 变化幅度)`。
只用一个都不够——dHash 对"整体平移"敏感但对小面积变化迟钝；网格占比反之。
两者叠加才能区分"全屏换页"和"角落里闪了一下"。

### 决策 2：拼图是成本手段，不是排版爱好

16 帧 → 1 张 4×4。按"一张图约等于固定一段视觉 token"粗算，感知成本直接降到 1/16，
而时间分辨率仍然保留 16 个切片（模型能从拼图里读出"先 A 后 B"）。标签 `#07 0.42`
把量化分数烧进图里，模型不必再猜哪帧更重要。

### 决策 3：UIA 优先，坐标兜底（而不是反过来）

`dsh-computer-use-win` 把 UIA 全能力钺开，代价是控件语义面太大、模型容易选错；
deputy 只留 4 个原语：`tree / invoke / setValue / sendInput`。
调用顺序固定为：

1. `invoke`（InvokePattern）/ `setValue`（ValuePattern）——语义动作，UI 挪位也不影响
2. `click(x, y)` —— 自绘界面（Electron/Qt/游戏）没有 pattern 时
3. `key` / `type`（KEYEVENTF_UNICODE 逐字符，绕输入法）

### 决策 4：selector 用"路径"，接受它的脆弱

`ref = { path: [i0, i1, ...] }`，从 RootElement 逐级走 `ControlViewWalker` 的第 i 个子节点。
RuntimeId 更稳但难序列化、跳进程不通用；XPath 式路径对模型友好、可读可回放。
**代价是界面一变路径即失效**——所以每个动作后必须 ROI 校验，`no-effect` 就重新取树而不是硬点。

### 决策 5：动作后只校验 ROI

`verifyAction` 同时看两个数：ROI 内变化量 `inside`、ROI 外变化量 `outside`。
判定三分：

- `no-effect`（inside < expect）→ 动作没生效 → 有限次重试或改策略
- `side-effect`（outside > 0.12）→ 出了弹窗/遮挡/焦点跑偏 → **立即上报**，不要继续叠动作
- `ok`

`side-effect` 这一档是 deputy 和纯截图流最本质的区别：它把"意外"变成了一等公民的返回值。

### 决策 6：预算先行，允许放弃

`Budget` 管四件事：拼图数、采帧数、步数、墙钟。任一项逼近上限就：
`normal → coarse → halt`。`coarse` 降采样率、只留 `major` 帧；`halt` 停止新增感知，
改为"带着现有证据汇报"。**桌面任务宁可交半成品 + 证据，也不要烧完 token 什么都不剩。**

## 4. 和两个参考实现的分工

| 维度 | dsh-computer-use-win | dsh-see-now | **dsh-deputy** |
|---|---|---|---|
| 主职 | 执行（UIA/键鼠/窗口管理） | 感知（直播画面 → 拼图） | **感知 + 执行 + 校验闭环** |
| 感知策略 | 按需截图，模型决定看哪里 | 连续采帧，按变化挑帧 | 连续打分分档 + 跨档才推 + 去重 |
| 校验 | 基本无（靠模型看下一张图） | 无（只负责"看见"） | **ROI 级 verdict 三态** |
| 隔离 | 无（操作主桌面） | 无（读屏） | **独立 Desktop + 受限令牌 + Job** |
| 成本控制 | 依赖模型自觉 | 拼图省 token | 拼图省 token **+ 预算强制降级** |
| 面向 | 通用桌面操作 | 直播/摄像头观察 | **有明确目标的办公任务** |

一句话：upstream 一个给"手"、一个给"眼"，deputy 补的是**"眼手之间的反射弧"**——什么时候该看、
看一眼值不值、做完到底成没成。

## 5. 失败模式清单（写在这里是为了后面别忘）

| 失败 | 现在怎么兜 | 后续 |
|---|---|---|
| 界面一动不动但动作成功（如复制到剪贴板） | `expect` 设 0，只判 `side-effect` | 加剪贴板/UIA 属性断言 |
| 路径失效 | `no-effect` → 重取树 | 加 fallback：按 name+type 模糊匹配 |
| 拼图里帧序混淆 | 标签烧进图 + 帧号 | 加时间戳与缩略高亮 |
| 隔离桌面里 UIA 树拿不到 | 目前只在当前桌面取树 | worker 进程首动作 attach |
| 死循环重试 | `maxRetriesPerAction` + 预算 | 加"同 verdict 连续 N 次"熔断 |
| 提权失败 | 明确报错，不降级到主桌面乱点 | 引导用户走 UAC |

---

## 6. 为什么这套东西值得单独成插件

因为它的价值不在"能点"，在**把桌面任务的可观测性做成模型能消费的形式**：
分数、包围盒、拼图、verdict。模型拿到的是判断依据，而不是"再给我一张截图"。
这也是为什么 `runner.mjs` 的依赖全部注入——没有 Windows 也能跑闭环测试，
算法层和平台层彻底解耦。
