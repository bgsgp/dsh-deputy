# 感知层：变化打分与 4×4 联系表

## 1. 为什么不用逐帧截图

一次 1280×800 全屏图，模型侧按视觉 token 粗算，一张就够把一个小任务的余量吃掉一大截。
桌面任务动辄 10~30 步，逐帧截图 = 上下文破产。
但反过来"只看最后一张"也不行：模型看不到过程，就无法判断"刚才那下点到了没"。

**正确姿态是压缩时间维度，而不是丢掉时间维度。** 4×4 拼图就是这个折中：
16 个时间切片，1 张图的成本。

## 2. 打分模型

输入：两帧同尺寸灰度图（`toGray`，BT.601 权重 77/151/28，右移 8 位）。

### 2.1 dHash（全局结构）

降采样到 9×8，逐行比较相邻像素得 64 bit：

```
bit[i] = gray[i] > gray[i+1] ? 1 : 0
distance = popcount(hash_a ^ hash_b)   // 0..64
hashPart = distance / 64
```

抗全局亮度漂移（截图增益不同、暗色模式切换）；对小面积变化迟钝——这正是它该有的性格。

### 2.2 网格变化（局部动作痕迹）

切 8×8 = 64 个格子，每格算平均绝对灰度差：

```
delta_cell = Σ|next - prev| / n / 255
hit_cell   = delta_cell > 0.06
ratio      = hit_cells / 64
magnitude  = Σ delta_cell / 64
```

`hit_cell` 的包围盒就是后续 `box`，直接被 `roi.mjs` 拿去当 ROI 锚点——感知和校验共用同一个坐标。

### 2.3 合成

```
score = 0.40 * hashPart + 0.60 * min(1, ratio*0.7 + magnitude*3)
tier  = still(<0.08) / minor(<0.26) / meaningful(<0.50) / major(≥0.50)
```

系数不是拍脑袋的：`ratio*0.7` 让"变了 1/3 格子"就接近满分，`magnitude*3` 补偿"变化面积小但
对比极强"的情况（一个黑色弹窗压在浅色页面上）。阈值在 `DEFAULT_SENSE` 里，可整体覆盖。

## 3. 挑选与去重

- 只有 `tier >= shipAt`（默认 `meaningful`）的帧进缓冲；
- 缓冲满 16 帧自动出图，也可手动 `flush`；
- 出图前算一个 `hashKey`（各帧 tier+score 拼接），和上一张相同则标记 `deduped` 且**不推送**
  —— 时钟跳秒、光标闪烁这类周期性变化不该反复占预算。

## 4. 拼图规格

`packSheet(frames, { cell: 192, gap: 6 })`，最多 16 帧，4 列自适应行数：

```
width  = 4*cell + 5*gap            = 798
height = rows*(cell+12) + (rows+1)*gap
```

- 每帧先缩放到 `cell` 方格（最近邻，速度优先）；
- 左上角画 `#07 0.42` 标签（内置 3×5 点阵字体，不引字体文件）；
- 深灰底（18）区分帧区与留白；
- 输出 8bit 灰度 PNG（`png.mjs` 手写 IHDR/IDAT/IEND + zlib，无第三方依赖）。
  灰度而非彩色：省 3/4 带宽，而桌面判断依赖的是布局与文字，不是色相。

## 5. 预算曲线

| 档 | 触发 | 行为 |
|---|---|---|
| `normal` | 拼图 < 70% 且时间 < 80% | 全量采帧 |
| `coarse` | 拼图 ≥ 70% | 采样率降到 40%，只留 `major` 帧 |
| `halt` | 拼图用尽 / 时间用尽 | 停止采帧，汇报现有证据 |

默认上限：12 张拼图 / 任务、16 帧 / 张、4000 次采帧、40 步、6 分钟墙钟。

## 6. 已知局限

- 滚动列表的连续小幅位移会被判成 `minor`，可能漏掉"列表滚到底了"这种关键状态。
  → 后续加"累计位移"通道：`minor` 连续 N 帧且方向一致，提升为 `meaningful`。
- 灰度丢色相，纯颜色状态变化（如"变红了=报错"）识别不到。
  → 后续在 `cell` 内加一个饱和度通道的低分辨率统计。
- 拼图内帧序靠标签维持，模型偶尔会读错顺序。
  → 后续给每帧加 2px 彩色左边框编码序号（用灰阶阶梯近似）。

## 7. 语义观察层：为什么不只用像素

`deputy_sense` 回答「画面变了多少」，`deputy_see` 回答「屏幕上有哪些窗口和控件」。像素层便宜、通用，
但对「按钮叫什么、输入框在哪、点没点中」只能猜；语义层直接给控件路径与可用模式，动作就能按名字走。分工：

- 要知道「有没有变化 / 变化多大」→ 像素（`deputy_sense`、ROI 校验）；
- 要「点这个按钮 / 往那个框里写字」→ 语义（`deputy_see` + `kind: "uia"`）；
- 语义拿不到（Chromium/UWP）→ 退回像素 + 键鼠，并在 [docs/DESKTOP.md](DESKTOP.md#62-观察层deputy_see-与语义动作) 里如实标注限制。

对照豆包的实现（`aha_cua.dll`：UIA + BitBlt + SendInput 同一进程里组合），这里把两层拆成两个工具，
模型按任务挑，失败路径也各自独立。
